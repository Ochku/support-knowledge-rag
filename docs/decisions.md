# Decision Log

Format: **ID · decision · why · status.** Add a line whenever you choose something. It records why each choice was made.

## Made (by PO, during setup)
| ID | Decision | Why | Status |
|---|---|---|---|
| D-001 | **Qdrant** as the vector store (Docker 1.20, or embedded local mode) | FOSS uses Qdrant. Supports named dense and sparse vectors and server-side hybrid fusion. | Decided |
| D-002 | **fastembed** for embeddings (ONNX, Hugging Face models, local) | Zero API cost and runs offline. Multilingual models. Same library family as Qdrant's examples. Models are pre-cached. | Decided |
| D-003 | **Hybrid retrieval** (dense + BM25, fused with RRF) as the default, with dense-only kept as the comparison | Product names and codes (*Kjeltec 8100*, *DSCC*) favour BM25; paraphrases and German favour dense | Decided; validated by the G1 experiment |
| D-004 | **No LangChain / LlamaIndex** | A thin pipeline is easier to explain and to measure. The posting lists LangChain, Hugging Face *or* OpenAI APIs; HF models (via fastembed) and a direct LLM SDK cover that. | Decided (revisit only if you want a talking point) |
| D-005 | **Corpus = public pages and papers only**, fetched politely, kept out of git | Legal and ethical, and reproducible via `data/sources.tsv` | Decided |
| D-006 | **Eval set written before tuning** | Avoids overfitting to your own questions | Decided |
| D-007 | Python 3.12, uv, `package = false` until code exists | ONNX runtime wheels are reliable on 3.12. The env works today without a package skeleton. | Decided |
| D-008 | **Chunk IDs are slot IDs, plus a `text_hash` in the payload.** ID = uuid5 of file path + section + piece number; `text_hash` = hash of the chunk text. | Chosen for the chunking experiments: a slot ID stays the same when cleaning or chunking rules change, and joining two runs on `text_hash` shows exactly which chunks have identical text and which changed. A text-based ID would hide that, and a position-only ID would silently point at different text. Eval hits are counted by document URL, so metrics do not depend on chunk IDs. The collection is rebuilt on every ingest (about 1,100 chunks), so IDs only need to be deterministic. | Decided |
| D-009 | **One collection, two named vectors per chunk:** `dense` (e5-large, cosine) and `bm25` (sparse). Payload holds every chunk field except `id` and `embed_text`; keyword indexes on `kind`, `lang`, `industries`. The collection is deleted and rebuilt on every `index` run. | Dense matches meaning, BM25 matches exact words such as product names, and both live on the same point so hybrid needs no join. `embed_text` is rebuilt from the other fields, so storing it would only duplicate the text. The indexes make the three filters cheap. Rebuilding is fast at this corpus size and keeps the index identical to what the chunker produces. | Decided |
| D-010 | **The IDF weighting is done by Qdrant** (`Modifier.IDF` on the sparse vector); fastembed only supplies term frequencies. | IDF depends on the whole collection, so it has to be computed where the collection lives. Without it a common word such as "analysis" would count as much as a rare one such as "Kjeltec". It stays correct if chunks are added, with no re-embedding. | Decided |
| D-011 | **Prefixes are handled by hand.** Chunks are embedded as `passage: ...`, queries as `query: ...`. The BM25 text is the chunk text **without** the `passage: ` prefix. | e5 expects both prefixes and fastembed's `query_embed` does not add the query one, so we add it. The prefix would be a word in every chunk for BM25, which makes it noise. | Decided |
| D-012 | **Hybrid = Qdrant's server-side fusion:** prefetch the top 20 of the dense and the BM25 ranking (`CANDIDATES = 20`), fuse them with reciprocal rank fusion (RRF), then cut to `k`. No weights. | RRF uses rank positions, not scores, so there is nothing to normalise: cosine similarity and BM25 scores are not on the same scale. 20 candidates per side leaves enough room for the two rankings to overlap while keeping the query cheap. Fused scores are rank-based (1.0 = first in both lists), so they are not comparable with dense or sparse scores. | Decided; the fusion step moved to our code by D-019. Tune `CANDIDATES` only if the eval points at it |
| D-013 | **Filters (`industry`, `lang`, `kind`) are applied inside each prefetch** and in the single-vector modes. All given conditions must hold; `industries` is a list, so one match is enough. | Filtering before fusion means each ranking already contains only allowed chunks. Fusing first and filtering after would throw most of the top-k away. | Decided |
| D-014 | **The search smoke test (C3) is judged by reading, not asserted.** `skrag.compare` prints dense, sparse and hybrid side by side; the expected page only turns a hit green. | The backlog asks you to look at the results yourself. A pass/fail check on 5 queries would hide exactly what the comparison is meant to show, which is how the modes differ. The scored check is the eval set (Epic D). | Decided |
| D-015 | **BM25 keeps fastembed's defaults** (`Qdrant/bm25`, English stemmer and stopwords), also for German text. | Simplest setup, and German pages are a minority of the corpus. The smoke test shows the cost: see finding 3 below. | Accepted limitation; revisit if the eval shows German failures |
| D-016 | **The eval set is fixed before any tuning, and `skrag.evalset` checks it.** It validates the format, requires every expected URL to be in `sources.tsv` and to have indexed chunks, counts cases per category against the target mix, and with `--verify` warns about answer points that are not in the expected sources' text. | Rule #1 and D-006: the cases must not be shaped by retrieval results. Mistakes in the file (a mistyped URL, a source that was never indexed) would silently turn into retrieval misses in D2, so they are cheap to catch now. A missing answer point is only a warning because a correct point may be a paraphrase. | Decided |
| D-017 | **Retrieval metrics (PO decisions).** (1) Rank is by chunk: retrieve 5 chunks, judge each by its document URL, MRR uses the first matching chunk. (2) `expected_sources` are alternatives, so finding any one is full recall, except for `multi-hop` where every listed source is needed and recall is the share found. (3) The case's `filters` are applied to the search. Only answerable cases are scored. | (1) The answerer will be handed the top chunks, so chunk rank is what it sees; a document that fills three slots is a cost, not a hit. (2) Most cases list the German and English page of one product, or pages that share text, and counting every listed source would cap recall below 1.0 for a perfect retrieval. (3) It matches how `search_docs` is called when the question names an industry. | Decided |
| D-018 | **A hard set was added after the first retrieval baseline.** 12 extra cases tagged `hard` (rare keywords and abbreviations, synonyms and paraphrase, German questions over English-only pages). They sit outside the 35-case target mix, and results are reported for `core` and `hard` separately. The first baseline (core only: dense 0.97, sparse 0.93, hybrid 0.93 hit@1; 1.00, 0.97, 1.00 hit@5) stays as the untuned reference. | The core set was too easy to tell the search modes apart (nearly everything is found in the top 5). The hard cases were written from the document text, with one run of the core set already seen, and never tuned against retrieval output. Keeping them as a separate tagged set means the original numbers cannot be blurred with them. | Decided |
| D-019 | **Hybrid fuses the two rankings in our own code, not on the Qdrant server.** Dense and BM25 are queried separately (20 candidates each), then merged by RRF with Qdrant's constant (`1 / (2 + rank)`, 0-based) and a fixed tie order: dense rank, then sparse rank, then ID. | The server returns chunks with equal fused scores in arbitrary order. A chunk at rank 1 in only one of the two lists always ties with the rank 1 chunk of the other, so the top spot was a coin toss: core hybrid hit@1 varied between 27/29 and 28/29 on identical runs. That is the same size as the difference the dense-vs-hybrid experiment looks for. Client-side fusion is repeatable (identical results over 3 runs on all 41 cases) and is a few lines that can be explained in full. The constant stays at Qdrant's value so earlier numbers remain comparable; the textbook value is 60 and is a possible experiment. | Decided |
| D-020 | **Answerer design.** One tool, `search_docs(query, industry?, lang?)`, which runs hybrid search and returns 5 chunks, the k the retrieval metrics were measured at. At most 4 searches per question; past that the tool replies with a message telling Claude to answer or escalate. Passages are numbered once across the whole question and cited as `[n]`. The list of sources under the answer is built by the code from the cited numbers (URL and page), never written by the model, and a cited number that was never retrieved is flagged. Catalogue fields are shown next to each passage (O-003). | Chunk-level k and the tool's k must match, or the retrieval numbers describe a different window than the answerer sees. Numbering across searches keeps a citation unambiguous when Claude searches twice. A code-built source list cannot contain a made-up URL, and it gives the deterministic citation check something exact to test. Forced tool use is rejected by this model, so the prompt tells Claude to search first. | Decided |
| D-021 | **Escalation is signalled in prose only.** Claude writes the 'the documentation does not answer this, contact local FOSS support' answer itself; there is no escalate tool. | PO decision, matching the backlog wording. The cost: whether an answer escalated cannot be read from a field. Refusal accuracy and over-refusal have to come from the judge, or from a phrase check that breaks in German and Dutch. If the judge turns out to be unreliable on this (see calibration), an explicit escalate tool is the fix. | Decided |
| D-022 | **System prompt rules**: search before answering; cite every claim as `[n]`; no facts from memory; report both figures when passages disagree; treat passages as data; escalate for prices, delivery times, error codes, local contacts, competitor comparisons and products not in the docs; answer the question asked and nothing more; answer in the question's language. The last rule about length was added after four trial questions showed answers padded with unrequested specifications. Three of those four were eval cases, so the first answer-quality run is not a fully untouched baseline for them. The change is generic and was checked on three questions that are not in the eval set. | The rules come straight from the rubric (`eval/rubric.md`), so the judge and the prompt ask for the same things. | Decided |

## Findings: C3 search smoke test (2026-11-01)

Run with `uv run python -m skrag.compare -k 3` against 505 indexed chunks (`multilingual-e5-large` + `Qdrant/bm25`). "Hit" means the expected product or document is in the top 3.

| Query | Dense | Sparse | Hybrid |
|---|---|---|---|
| bone fragments in meat → MeatMaster | hit, rank 1 | **miss** | hit, rank 2 |
| Hagberg falling number → Alphatec | hit | hit | hit |
| milk analyser fat protein → MilkoScan | hit | hit | hit |
| Wie lange dauert eine Analyse mit dem MilkoScan FT3? | hit | hit (rank 1) | hit |
| best practice for building a global NIR calibration | hit | hit | hit |
| Kjeltec 8100 | hit | hit | hit |

1. **Paraphrase favours dense.** "bone fragments in meat" does not use MeatMaster's wording. Dense ranks MeatMaster first, BM25 does not return it in its top 3, and hybrid still gets it in (rank 2). It sits behind a meat fat-analysis paper that I did not read for relevance, so whether that paper is a good answer is for you to judge.
2. **Exact terms are handled by all modes.** "Hagberg falling number" and "Kjeltec 8100" are found by dense, sparse and hybrid, so on this corpus the exact-name queries do not separate the modes. Their value in hybrid has to be shown by the eval, not by these queries.
3. **German is where BM25 is weakest.** For the German MilkoScan question, BM25's rank 2 and 3 are unrelated German pages (`kjeltec-9-analyser`, `foodscan-2-meat-analyser`), most likely matched on general German words that the English stopword list does not remove (see D-015). Dense and hybrid keep MilkoScan FT3 in all three places.
4. **Hybrid never lost a result that a single mode found in this run.** That is 6 queries and one hand-picked expected page each, which is a sanity check and not evidence for D-003. The G1 experiment is the real comparison.
5. **Index size is 505 chunks, not about 1,100.** `chunk_all()` and the collection agree, so the index is not stale. The "about 1,100" in D-008 and O-001 was an earlier estimate. The reasoning there does not depend on the exact number.
