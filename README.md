# support-knowledge-rag

A small, **measured** retrieval-augmented support assistant over public product documentation for food and agricultural analytics instruments (FOSS).

It uses Qdrant hybrid search (dense + BM25) for retrieval. Claude writes the answers with citations, or escalates to human support when the sources don't cover the question. An evaluation harness measures retrieval quality and answer quality, so changes can be compared against numbers rather than impressions.

> **Status:** works end to end, from documents to cited answers to a judged evaluation run. One planned experiment is **not done**: dense-only vs hybrid has been compared on retrieval but not on answers. The eval set is small and the answers are judged by an LLM that was checked on little data. Read [Results](#results) and [Limitations](#limitations) before relying on any number here.

## Goals
- **Grounded answers:** every claim cites the document (and page) it came from.
- **Knows when not to answer:** questions the corpus can't answer, such as prices, error codes or local contacts, get escalated instead of guessed.
- **Multilingual:** a question in one language can be answered from sources in another, for example German questions over English documents.
- **Measured:** hit@k, recall@5 and MRR for retrieval, plus an LLM-judge rubric for answers, tracked per search mode and per question category.

## How it works
Documents are parsed and cut into about 400-token chunks along their headings, embedded locally (`multilingual-e5-large` for meaning, BM25 for exact words) and stored in Qdrant. The assistant is Claude with one tool, `search_docs`, which runs a hybrid search and returns five numbered passages. Claude decides what to search for, at most four times, and cites the passages as `[n]`. The source list under each answer is built by our code from the numbers Claude cited, never written by the model. Diagrams: [`docs/architecture.md`](docs/architecture.md).

Counts are shown as k/n. The 35 **core** cases were written before any tuning. The 12 **hard** cases were added after the first retrieval baseline, to separate the search modes, and are reported apart.

Answering the 47 cases cost $1.89 and judging them $1.68. The whole run took 11 minutes.

**What the run shows**
- The four cases that did not pass are `spec-003`, `spec-009`, `which-002` and `multi-001`. In three of them the judge did not dispute the content, but a claim stood in a sentence with no `[n]` (the marker sat on the next sentence or further down) and its *Cited* criterion failed. In `which-002` Claude added a framing for a second product that its passage does not support. No failure was an invented figure, a wrong language or a missed escalation.
- The judge passed all six unanswerable cases (a price, a delivery time, an error code, a phone number, a competitor comparison and a product that does not exist): each was escalated and none got invented facts.
- The expected page was among the retrieved passages in all 41 answerable cases, so none of the four failures comes from retrieval.
- The judge flagged one over-refusal, in `xling-003`. Its own reason says the answer is complete and escalates only for storage temperatures that the documents do not give. I read that as a false flag by the judge. It is not a blocking criterion, so the case still passed.

**What it does not show.** This is one run, on 47 cases I wrote, judged by the model that answered them. It is not an accuracy figure. One case is worth about two percentage points. See Limitations.

### How far the judge can be trusted
- **Hand labels:** I labelled 10 answers before the judge scored them (label times 19:01 to 19:11, first judge verdict on them 19:13; [`eval/calibration.jsonl`](eval/calibration.jsonl)). The judge agreed on 10 of 10. All 10 were passes, so this shows the judge does not fail good answers and says nothing about whether it catches bad ones.
- **Injected defects:** nine answers with one deliberate defect each (a flipped verdict, an invented fix, an invented phone number, an accepted false premise, a wrong or unretrieved citation, the wrong language, an over-refusal, and a control that should still pass; [`eval/calibration-negatives.jsonl`](eval/calibration-negatives.jsonl)). The judge caught 9 of 9 on the criteria written down in advance. The defects are crude and were written by an AI assistant, so this is a check that it notices these kinds of error.
- **One label is arguable:** `unans-004` is labelled pass. The answer escalates correctly but also gives the Danish head-office phone number from a white paper's footer. A stricter reader might fail it. Details in [`docs/decisions.md`](docs/decisions.md).

## Limitations
- **Small eval set, one author.** 47 cases (41 answerable), written and checked by one person. Three of them were among the trial questions that shaped the system prompt (D-022), so the run is not an untouched baseline for them. Differences of one or two cases are noise.
- **The judge is not independent.** It is the same model as the answerer and could favour its own style. Only 10 real answers were hand-labelled, all passes. None of the 47 verdicts in the run above has been checked by a person: the 10 hand-labelled answers came from earlier runs. The judge's biggest effect here is strictness about where a citation sits, which decided three of four failures, and one of its non-blocking verdicts contradicts its own reason.
- **One run, no variance estimate.** Answers vary between runs. `spec-003` was a pass in the answer I labelled and a fail in this run, because the citation moved to another sentence. Repeating the run would show how much the 43/47 moves.
- **Dense-only vs hybrid is not done end to end.** The retrieval numbers above cover all three modes. Only the hybrid configuration was answered and judged.
- **Easy retrieval.** Many questions name a product or a clear topic, and the index is about 500 chunks from public pages. The hard set separates the modes a little. These numbers say little about a large, messy knowledge base.
- **Public documents only.** There are no prices, no error-code lists and no local contacts, so the assistant correctly refuses them. It cannot help with the questions a real support engineer asks most.
- **Prompt injection is untested.** The prompt tells Claude to treat passages as data, and the rubric has a criterion for it, but no case in the set contains a poisoned passage.
- **Language check is a heuristic.** It knows English, German, Dutch and Danish by function words and abstains on very short answers. The judge covers the rest.
- **Cost and latency** come from one run on one machine: about $0.040 per answer, plus the judge, and a mean of 6.4 s.

## What I'd do next
1. Run the dense-only vs hybrid comparison on answers, and repeat each run three times to see the spread.
2. Fix the citation placement the judge keeps failing (put the marker on the sentence that states the figure), and measure whether that moves the pass count.
3. Label the four failures and a random sample of passes by hand, and compare with a judge from another model family.
4. Add a product lookup tool for list and comparison questions, which top-five search handles badly.
5. Add cases with poisoned passages, and with questions that mix two products.

## Run it
Requirements: [uv](https://docs.astral.sh/uv/), Python 3.12, Docker (optional) and an Anthropic API key.

```sh
uv sync                      # Python 3.12 venv + locked deps (dev group included)
cp .env.example .env         # add ANTHROPIC_API_KEY, or use `ant auth login`
docker compose up -d         # Qdrant at http://localhost:6333/dashboard
                             # no Docker? use embedded mode: leave QDRANT_URL empty, keep QDRANT_PATH
```

The corpus is not in the repository (see [Data](#data)). Fetch the documents listed in `data/sources.tsv` into `data/raw/`, then:

```sh
uv run python -m skrag.index                     # chunk, embed and index the documents
uv run python -m skrag.search "bone fragments in meat"
uv run python -m skrag.evalset check             # validate eval/cases.jsonl
uv run python -m skrag.retrieval_eval            # hit@k, recall@5, MRR for dense, sparse, hybrid; free
uv run python -m skrag.answer "How long does a MycoFoss test take?"   # add --trace to see every step
uv run python -m skrag.answer_eval               # answer and judge all cases: about $3.60, 11 minutes
uv run python -m skrag.answer_eval spec-001 unans-001                 # or just a few
```

Judge checks:

```sh
uv run python -m skrag.judge spec-002            # judge a logged answer
uv run python -m skrag.calibrate label <case ids>   # label answers by hand, one prompt each
uv run python -m skrag.calibrate report          # compare your labels with the judge
uv run python -m skrag.negatives                 # the nine injected defects, about $0.20
uv run pytest && uv run ruff check               # tests and lint
```

Embeddings run locally with [fastembed](https://github.com/qdrant/fastembed). Set `FASTEMBED_CACHE` (default `.cache/fastembed`) so the models aren't downloaded again on every run. Model choices are configured in `.env`.

## Data
The corpus consists of public pages and PDFs from FOSS's website. It is third-party content, so it is **not redistributed in this repository**. `data/raw/` and all derived artefacts (`data/processed/`, local Qdrant storage, `results/`) are gitignored. `data/sources.tsv` lists the source URL of every document so the corpus can be rebuilt.
